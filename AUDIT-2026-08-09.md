# Adversarial audit — 2026-08-09

**Scope:** `contracts/InheritanceVault.sol`, `contracts/NotifySubscription.sol`,
`notify/watcher.js`, `scripts/notify-scenario.ts`.
**Method:** five independent reviewers with distinct lenses (accounting/stranding, token
edge cases and reentrancy, state machine and griefing, subscription math, off-chain alerting),
then a second adversarial round aimed exclusively at the round-one fixes.
**Verification rule:** a finding is reported only if it was reproduced as a failing test or an
executable scenario step. Claims that could not be made to fail were rejected and are listed.

**Result:** 12 defects fixed (2 high, 5 medium, 5 low on chain; 5 critical, 6 high off chain —
counted below by area). Baseline 58 tests → **63 unit tests + 14 scenario steps, all green.**

---

## Round 1 — findings against the original code

### A-01 · MEDIUM · Cross-function reentrancy strands a deposit forever
`InheritanceVault.topUp` measured a deposit with `balanceOf` before/after `safeTransferFrom`,
then wrote the result to storage. A token with a receive hook (ERC777-style) whose owner also
owns a vault could, inside that transfer, call the then-unguarded `withdraw` and close the
vault. Control returned and `topUp` wrote the deposit onto a **closed** vault: unreachable by
owner, heir and admin, and invisible to `sweepSurplus` because `totalLocked` still counted it.

*Fix:* `nonReentrant` extended across the whole state machine (`withdraw`, `initiateClaim`,
`abortClaim`, `finalizeClaim`, `checkIn`, `checkInMany`, `checkInByChain`, `setBeneficiary`,
`setInactivityPeriod`, `extendHorizon`, `setCheckInChain`), plus a post-transfer state re-assert
in `topUp`. `checkInMany` was rewritten to inline its logic rather than call `checkIn`, so the
shared guard cannot self-deadlock.
*Test:* `Audit.ts` A-01 (`ReentrantToken` helper added).

### A-02 · HIGH · The horizon did not bound a hostile owner key
Past `absoluteDeadline`, `_resetClock` clamps `deadline` to a value already in the past. So a
claim displaced after the horizon could be displaced again in the **next block** — an unbounded,
zero-cooldown denial of inheritance for the price of gas. `abortClaim` had no horizon check, and
four "soft" owner actions cleared a pending claim through `_clearPending`.

*Fix:* `abortClaim` reverts `HorizonReached` past the horizon; `_clearPending` refuses to
displace a claim past the horizon except via `extendHorizon`.
*Test:* `Audit.ts` A-02 (four cases).

### A-03 · MEDIUM · `checkInMany` was all-or-nothing and could brick a whole estate
One vault reaching a horizon chosen years earlier reverted the entire batch, so a keeper
following the documented split-estate pattern would silently stop refreshing **all** vaults and
hand every heir a premature inheritance. Same for one vault with a claim pending.

*Fix:* skip un-checkable vaults, return `refreshed`, revert `NothingCheckedIn` only if zero.
*Test:* `Audit.ts` A-03 (three cases).

### A-04 · LOW · The claim fee could be raised under a claim in flight
`finalizeClaim` read the global rate at execution time, so an admin could sandwich a settlement
— raise the fee to the vault's ceiling immediately before, drop it immediately after — taking a
fee the heir had every public reason to believe was lower. Public state read unchanged.

*Fix:* the effective rate is locked at `initiateClaim` and can only fall thereafter.
*Test:* `Audit.ts` A-04 (three cases).

### A-05 · LOW · Revert data named a value that was never compared
`createVault` reverted `HorizonNotExtended(block.timestamp, given)`, describing a *valid*
extension being refused and hiding the actual floor.
*Fix:* new `HorizonTooSoon(minimum, given)`. *Test:* `Audit.ts` A-05.

### Documentation corrected (each was materially false)
- `receive()` claimed native value could never enter outside the accounting lanes; `SELFDESTRUCT`
  and block rewards can force-feed it (harmlessly, into surplus).
- The rebase note said "strands or manufactures surplus". The truth is sharper and is now
  stated: a **positive** rebase accrues yield to the admin as sweepable surplus; a **negative**
  rebase makes the credit lane first-come-first-served, so the last claimant recovers *nothing*.
- `checkInByChain` did not disclose that an heir can front-run a late chain check-in and kill the
  recovery path permanently. Now documented (see open question OQ-1).
- An inherent, unfixable limitation is now stated: value credited to an address that can neither
  originate a call nor receive native value is stuck, and no admin rescue exists **on purpose**.

### Off-chain (watcher) — five criticals
| # | Defect | Consequence |
|---|---|---|
| W-01 | `state.json` written non-atomically and parsed at module load | one truncated write bricked every future run — total silent outage |
| W-02 | Dedupe key burned at enqueue, before delivery | a typo'd address permanently consumed the veto alert; fixing the config did not bring it back |
| W-03 | `deliver()` had no per-message error handling | one permanently-rejected recipient blocked every alert queued behind it, forever |
| W-04 | Subscription read outside the try/catch | one malformed config row killed the whole run and discarded alerts already queued |
| W-05 | Veto alert unrecoverable after settlement | an outage spanning one challenge window lost it with no trace |

*Fixes:* atomic write + `fsync` + tolerant load; keys burned only on successful delivery;
per-message isolation; every RPC read guarded and failing **open**; `ClaimInitiated` log
backfill. Plus six high/medium: heir alerts no longer gated on the owner's billing, dedupe keys
include the recipient and use on-chain (normalized) addresses, chain-exhausted alerts re-arm per
installed chain, the veto alert escalates instead of firing once, expired/claimable conditions
re-notify weekly, and settlement/closure is now reported at all.

## Round 2 — findings against the round-1 fixes

Mandatory per project convention. It found that **two of the round-one fixes were incomplete**,
one of them demonstrated by a test that claimed to prove the opposite.

### B-01 · HIGH · A dust withdrawal was a better `abortClaim`
A-02 exempted `withdraw` from the horizon rule on the reasoning that it "actually moves the
money out". A **1 wei** withdraw moves nothing out: same effect as the abort, same gas, and you
keep the wei. The loop was fully intact — and `Audit.ts` A-02 was performing exactly that
sequence and asserting success.

*Fix:* past the horizon a partial withdraw no longer displaces a claim (the heir simply inherits
less); a full withdraw closes the vault, ending the claim by ending the vault.
*Test:* `Audit.ts` A-02 "a dust withdrawal is not a backdoor veto" and "a full withdrawal … still
closes the vault".

### B-02 · HIGH · `extendHorizon` accepted a horizon still in the past
The remaining sanctioned override required only `new > current`, not `new > now`. An owner past
their horizon could extend by **one second**, clearing the pending claim and leaving `deadline`
pinned in the past — the same unbounded loop, wearing the one costume `_clearPending` still
admitted. The frontend made it reachable by accident: the date prompt accepts today's date.

*Fix:* a horizon must be at least one full inactivity period in the future, restoring a real
cooldown per override. *Test:* `Audit.ts` "extendHorizon cannot be satisfied with a horizon that
is still in the past".

### B-03 · MEDIUM · `checkInMany` still reverted on an unknown vault id
A-03 removed two of three revert paths. `NoSuchVault` remained, so one stale id in a keeper's
list preserved the whole trap. *Fix:* out-of-range ids are skipped. *Test:* `Audit.ts`.

### B-04 · LOW · `setCheckInChain` installed chains that could never fire
Past the horizon it succeeded, cleared the "chain exhausted" warning bit, and left the owner
believing the lost-wallet recovery path was armed — the exact green-toast lie `checkIn` reverts
to avoid. *Fix:* reverts past the horizon. *Test:* `Audit.ts`.

### B-05 · LOW · The fee lock made `feeBps` lie about being a creation snapshot
A-04 mutated `v.feeBps`, so `getVault` disagreed with the `VaultCreated` event with no event
explaining it, and a rate locked during a promotion survived an aborted claim permanently.
*Fix:* the locked rate moved to its own `lockedFeeBps` field; the creation ceiling is immutable
again. *Test:* `Audit.ts` "a rate locked during a promotion does not survive an aborted claim".

### B-06 · CRITICAL (off-chain) · The veto email told owners to do something that reverts
Past the horizon, `abortClaim` and every soft action now revert (by A-02/B-01). The alert still
said "any action from your wallet cancels the claim". An owner following it exactly would hit a
bare revert while the window ran out. *Fix:* the email branches on `horizonReached` and names the
two things that still work.

### B-07 · HIGH (off-chain) · Backfill could never have fired in production
`BACKFILL_BLOCKS = 200_000` is ~4.6 days on Base — shorter than `MIN_CHALLENGE` (7 days), so the
triggering log had always scrolled out of range by the time settlement was visible. Public RPCs
also reject 200k-block `eth_getLogs` outright, and that throw did not mark the run as failed.
*Fix:* paged scan (9k blocks) with a persisted per-watch cursor, committed only after the alerts
it produced were delivered; backfill failure now marks the run failed.

### B-08 · HIGH (off-chain) · Three more silent-loss paths
`state.seen` (the trigger for settlement notices) was burned before delivery and keyed by owner
alone, so a failed send lost the notice permanently and a second watch on the same owner never
got one; unbounded retry of a hard-bouncing address risked provider suspension, which would
silence every customer; and a lapsed subscriber was not told their timer had expired **while the
heir was being told to claim**.
*Fix:* `seen` advances only for delivered notices and is keyed per watch; a 12-attempt cap with a
dead-letter log; and the billing gate now covers *only* the advance-reminder ladder — every alert
that means something is happening is sent regardless of billing.

### B-09 · MEDIUM (off-chain) · Backfill reported an *aborted* claim as settled
The state check read the vault while the loop iterated events, so an older, vetoed claim on a
later-settled vault produced "your estate settled on \<date you actually vetoed\>".
*Fix:* only the claim whose timestamp matches the settled vault's `claimInitiatedAt` is reported.

### B-10 · MEDIUM (off-chain) · A lagging RPC could fabricate a settlement notice
A replica omitting a vault made it look closed. *Fix:* every disappearance is confirmed with
`getVault` before alerting; unconfirmed ids stay under watch.

Also fixed: `saveState` guarded (an unwritable state file was a permanent duplicate storm),
degraded modes now exit non-zero instead of reporting green, the veto "escalation" no longer
fires a duplicate within one cron interval on a 7-day window, and heir alerts are suppressed —
with a notice to the owner — when the configured heir no longer matches the on-chain beneficiary.

## Rejected claims

- **Re-entrant `initiateClaim` during a deposit.** Reported as a second face of A-01. Not
  exploitable: `initiateClaim` requires `msg.sender == v.beneficiary`, so the hook reverts on
  authorization, not on the guard. Covered by a test regardless.
- **Overflow in `NotifySubscription`'s pro-rata math.** Traced and refuted: `MAX_PREPAID` bounds
  the value that is cast, `msg.value * MONTH` would need ~4.5e70 wei, and 0.8.x reverts anyway.
- **`renounceOwnership` mutability override.** Legal Solidity; harmless.
- **Both-keys-lost is a permanent dead end.** True, and deliberate — disclosed as trust-model
  item T2. Any admin rescue hatch is an admin rescue hatch.

## Open questions (design decisions, not defects)

- **OQ-1 — the check-in chain sniping race.** An heir watching the mempool can front-run a chain
  check-in that arrives *after* the deadline lapses, permanently killing the recovery path.
  Letting `checkInByChain` cancel a pending claim would fix it but grants the paper seed veto
  authority, changing the documented trust model. Documented, not changed.
- **OQ-2 — `checkInMany` skips are invisible to wallets.** `refreshed` is returned but most
  callers discard return values, and there is no `CheckInSkipped` event. Adding one is cheap and
  probably right; it was out of scope for a fix round.
- **OQ-3 — no fee-ceiling slippage on `createVault`.** A vault's fee ceiling is set by the global
  rate at mining time, so an admin could raise it in the same block. Bounded at 1% by bytecode.

## Status

Pre-deployment. 63 unit tests and a 14-step end-to-end scenario pass. This audit was performed by
the same system that wrote the code — it is a substitute for neither a third-party review nor a
testnet soak, and the site continues to say so until both are done.
